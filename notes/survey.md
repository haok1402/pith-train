# Dense BF16 in PithTrain

This survey covers fork revision `f66bcc9`. The dense path supports the Qwen3.5-27B text tower with 64 SwiGLU decoder blocks, 48 Gated DeltaNet blocks and 16 gated grouped-query attention blocks. Each Gated DeltaNet block has 16 key heads and 48 value heads. The HF converter accepts both standalone text and nested multimodal checkpoints and imports the text tower. It skips vision and MTP weights. The fork's dense-support commit `a4225d9` reports a BF16 log-probability check against HF using Qwen3.8-27B weights. [Dense model](../pith-train/pithtrain/models/qwen35.py), [HF converter](../pith-train/pithtrain/modules/hf_converters/qwen35.py), [Qwen config](https://huggingface.co/Qwen/Qwen3.5-27B/blob/main/config.json).

## Current execution

- **Pipeline.** `setup_model()` always builds phases 0 and 1, wraps both with FSDP2, and constructs `DualPipeV`. `Qwen35MoeModel.__init__` partitions into `2 * pp_size` logical chunks, with chunks `r` and `2 * pp_size - 1 - r` on rank `r`. Even PP1 retains two chunks. Rank 0 holds the embedding and, on the return leg, the final norm and 248,320-class LM head. The Qwen3.5 partitioner shifts one decoder layer off the LM-head chunk when the mirrored layer-count constraint permits. PP8 requires at least 16 microbatches per step. [Setup](../pith-train/pithtrain/modules/training.py#L361), [partitioner](../pith-train/pithtrain/models/qwen35_moe.py#L52), [schedule](../pith-train/pithtrain/pipeline/dualpipev.py#L522).
- **Layer schedule.** Dense layers still enter stage 1 for attention and norms, stage 3 for the dense MLP, and stage 5 for the residual. They return no routing metadata, so stages 2 and 4 pass through. The engine detaches tensors at stage boundaries, drives separate backwards, and schedules deferred weight-gradient work. Dense BF16 linear wgrad accumulates into FP32 `main_grad` in its backward. The dense layer already has a contiguous reference forward, and the model has a full-depth `phase=-1` constructor. [Dense layer](../pith-train/pithtrain/models/qwen35.py#L37), [execution](../pith-train/pithtrain/pipeline/execution.py#L141), [linear](../pith-train/pithtrain/operators/linear.py#L252).
- **DP and ZeRO.** Stock training uses composable `fully_shard` per decoder block and separately around the edge modules, with optional `hsdp_replica`. The V schedule keeps its BF16 parameters and FP32 gradient accumulators materialized across the step, then reduce-scatters once and reshards. This is PithTrain's ZeRO-1 policy. For PP8 with eight GPUs, each pipeline rank has a single-rank shard group. There is no plain DDP training path on this revision. The fork's older `origin/haok/fsdp-zero-stages` branch adds per-class ZeRO-2/3 inside DualPipeV and is a reference for memory and gradient behavior. It does not provide a standalone dense trainer. [FSDP setup](../pith-train/pithtrain/modules/training.py#L301), [step finalization](../pith-train/pithtrain/pipeline/dualpipev.py#L546), [ZeRO branch](https://github.com/haok1402/pith-train/tree/haok/fsdp-zero-stages).
- **Activation checkpointing and compile.** Dense Gated DeltaNet inherits non-reentrant selective checkpointing in training and recomputes its depthwise convolution. The shared full-attention block enables selective checkpointing for FP8 training. Its policy also recomputes selected FP8 projections and keeps the attention and Gated DeltaNet custom-op outputs. There is no full-decoder checkpointing knob here. Dense stages 1 and 5 use full-graph `torch.compile`. The dense MLP stage is eager and calls fused SiLU-multiply; some surrounding operators have their own lowering or fusion. [Selective policy](../pith-train/pithtrain/models/qwen35_moe.py#L67), [dense compile boundaries](../pith-train/pithtrain/models/qwen35.py#L61).
- **Kernels.** Hopper uses the CuTe Gated DeltaNet forward/backward and custom causal convolution, FlashAttention-4 for GQA, fused SiLU-multiply and fused cross-entropy. BF16 projections use PyTorch GEMMs and FP32 wgrad accumulation. The FP8 switch uses DeepGEMM for eligible linears, caches quantized operands within each training step and supports FP8 FSDP gathers. The dense SwiGLU input quantization is shared by gate and up projections. The LM head is explicitly BF16. [Gated DeltaNet](../pith-train/pithtrain/operators/gated_delta_rule.py#L201), [head](../pith-train/pithtrain/models/qwen35_moe.py#L600), [weight gather](../pith-train/pithtrain/modules/fp8_param_gather.py).

## FSDP2-only route

Add an opt-in dense model and trainer entry point. Build the full text tower with the existing block reference forward and ordinary `nn.Module.__call__` at each block, since FSDP2 attaches hooks to that entry point. Use meta initialization, shard embedding, decoder blocks and LM head bottom-up before materializing weights, and keep the canonical parameter names used by the current HF and distributed checkpoint loaders. Start with the PyTorch FSDP2 hooks, BF16 parameter gathers, FP32 reduction and `reshard_after_forward=True`. The dense loop can use the current dataset and cross-entropy, one standard loss backward per microbatch, and the existing gradient clipping and optimizer after all microbatches. Preserve the current summed-gradient/global-token normalization when establishing parity. Keep all dense-only selection at the trainer boundary so MoE keeps its existing DualPipeV behavior. Use stock linear gradients initially, then measure the value of the custom `main_grad` hooks under per-backward reduction. Validate loaded logits, loss, gradients and a BF16 optimizer update before comparing throughput. [Existing reference forward](../pith-train/pithtrain/models/qwen35_moe.py#L643), [HF streaming loader](../pith-train/pithtrain/modules/hf_loader.py#L43), [PyTorch FSDP2](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html).

## Dense benchmark choices

Keep the 4K BF16 DualPipeV run as the control. Match weights, sequence length, global tokens and optimizer for each paired comparison. Track steady-state step time, peak allocated and reserved memory, and time spent in compute, collectives and optimizer work.

| Inherited choice | Dense comparison and expected effect |
| --- | --- |
| ZeRO-1 with step-wide unsharded weights and FP32 gradients | Use DP8 FSDP2 with per-block resharding and explicit prefetch. This cuts persistent memory and removes pipeline P2P. Two BF16 gathers plus an FP32 reduce-scatter for 26.9B parameters move about 188 GB per rank per microbatch, equivalent to 0.47 s at 400 GB/s if exposed. Measure whether retaining selected groups or using BF16 reduction improves throughput within the memory and numerical targets. |
| V-shaped chunks and five-stage overlap | Compare a dense 1F1B schedule and ordinary FSDP2. Dense stages have no expert dispatch or combine to hide, so stage overlap has to pay for itself through P2P or scheduling gains. Measure pipeline bubbles, launch gaps, and rank imbalance. For PP8, balance the head separately by time and memory because it adds 7.6 GFLOP/token of training work to rank 0. |
| Selective token-mixer checkpointing | Measure the inherited policy against saved activations and targeted recompute of MLP or norm intermediates. Check whether the memory savings enable a wider microbatch or 4K fit. Full block recompute adds about one forward pass of those blocks. Tiling the head and loss can instead avoid materializing about 1.9 GiB of BF16 logits per 4K sequence. |
| Microbatch of one sequence | Sweep local batch 1 and 2 at 4K at fixed global tokens. Wider GEMMs and fewer collectives per token can improve throughput. Activation and LM-head memory rise with local tokens. The current fused cross-entropy uses 64-bit row offsets. |
| Existing Hopper kernels and stage-level compilation | Benchmark the exact 5120×17408 SwiGLU, 16:48 Gated DeltaNet and 24:4 GQA shapes. Compare eager and compiled full dense blocks, and separate from-scratch compilation from steady-state time. Halving a path responsible for 10% of wall time raises throughput about 5%. |
| FP8 recipes after BF16 | MLP projections account for 65% of useful 4K FLOPs. If they take 60% of measured time and speed up 1.5× including quantization, throughput rises 25%. FP8 gathers halve eligible BF16 parameter bytes. Measure GEMM and gather changes independently. |

These gains are conditional estimates. At 4K the 50% target is approximately 25,199 aggregate tokens/s on eight H200s at 989 dense BF16 TFLOP/s each. [FLOPs calculator](../bench/summarize.py), [Megatron Bridge FLOP formulas](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/main/src/megatron/bridge/training/utils/flop_utils.py), [NVIDIA H200 specifications](https://www.nvidia.com/en-us/data-center/h200/).

## Measured dense comparisons

- Compiled FSDP2 reached 42.66% MFU at 4K on the full pretrained text tower with eight H200s, global batch 64 and FP32 gradient reduction. The stock PP8 control used batch 256 and Muon, and hit a rank-0 OOM on its second step. These runs establish feasibility and memory pressure for their respective configurations. [FSDP2 results](fsdp2.md), [PP8 control log](../logs/bf16-1263388.log).
- On the two-H200 eight-layer FSDP2 proxy, full-block compilation increased throughput by 12.8% over eager. BF16 gradient reduction increased throughput by 5.6% at fixed prefetch, and increasing the microbatch from one to two increased it by 17.8% at fixed global tokens. Full block checkpointing reduced the peak allocation by 7.24 GiB and reduced throughput by 11.7% in the matched one-sequence proxy. These measurements support enabling compilation and measuring the memory trade-offs at full scale. [FSDP2 ablations](fsdp2.md).
- At the 4K operator shapes, FA4 took 2.20 ms for gated attention forward and backward versus 3.12 ms with SDPA. The in-place cross-entropy path took 49.34 ms for LM head and loss versus 55.82 ms for the native loss path, with 8.59 versus 15.63 GiB peak allocated. [Hopper kernel measurements](kernels.md).
